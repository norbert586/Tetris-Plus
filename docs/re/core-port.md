# Phase 6: the TypeScript core (2026-10-17)

Puzzle Mode's game logic now runs in TypeScript (`web/src/core/`), and it behaves exactly like
the original. The exit criterion is met: **every movie of the trace corpus replays on the core
with a trace identical to the original's**, every traced field on every tick (§4):

- the five Phase 5 movies, 34,298 ticks;
- three new scenario movies that reach the screens Phase 5 didn't (zone clear, ending and
  credits, name entry with a rank, the hidden stage select, the end of the 100-stage run),
  19,182 ticks (§5).

That is 53,480 ticks of the original matched by the port, from power-on routes through every
screen of Puzzle Mode.

What else this phase delivers:

- **Function-level checks against the original.** 19 original routines ran in Unicorn on 11,500
  generated game states; the core's versions change the same memory, return the same values and
  make the same `rand()` calls and sounds in every case (§6).
- **The whole of Puzzle Mode's logic, not just gameplay.** All fourteen screens for both
  players: menus, password entry, the map, story scenes, stage intro and rules panels, play,
  pause and its menu, continue, stage and zone clear, the ending and credits, name entry, the
  save screen and player 2's idle screen. The only thing left out is memory-card I/O (§7).
- **A step function for the shell.** `Game.step(padWord)` runs one tick; `Game.m` is the state;
  sound and music requests come out as events (§2).

## 2. How the core is built

**State lives where the original keeps it.** The core models the PlayStation's main RAM as one
2 MB buffer addressed with the original's addresses, and keeps every variable there: PAZLE.EXE's
globals, the boot program's shared state block (`state` = `0x8003E668`) with its 1,050 sprite
objects. Ported functions read and write the same addresses as the original routines they
replace, through named constants. That choice made the port checkable at every level:

- the tracer reads the same addresses as the emulator's (`trace.ts` is generated from
  `re/lua/trace_fields.lua`);
- the Unicorn fixtures compare memory word for word (§6);
- a save state is a copy of one buffer, and the core can start from an emulator RAM dump
  (`new Game({ram})`), which helps debugging.

**Tables are the program's own data.** `rom.ts` holds PAZLE.EXE's read-only block
(`0x80094000`-`0x800955D3`) and its initialised data (`0x800D4FB0`-`0x800ED7FF`), loaded at their
addresses: shapes, levels, stage records and layouts, professor scripts, sprite animations,
message text, sound tables, dispatch-free constant tables. Code is not included.
`docs/spec/data/*.json` stays the readable copy of the gameplay tables.

**The starting state** is what PAZLE.EXE finds when it starts: its data, zero BSS, and the
shared block's best times, ranking tables, option settings and the menu's row count as the
boot program left them (`boot-state.ts`, captured from an emulator run at tick 1). The frame
counter and the BIOS `rand()` seed are parameters (`counter`, `seed`); the corpus runs start at
1001 and `0x4327D505`.

**One tick** (`Game.step(pad)`), in the original's order:

1. The previous iteration's tail: `pad_read` stores the pad word (pad 1 low, pad 2 high), the
   main loop's `rand()`, the soft-reset check.
2. `state+0x40 += 1`, then `phase_dispatch`: player 1's screen and `pause_check`, then player
   2's, then the two-player flag.
3. `objects_draw`'s part that changes state: every live box-fill object (kind −1) draws a box
   whose colour costs three `rand()` calls.

Sound effects and music requests are collected per tick in `game.se` and `game.bgm` (the
arguments of `se_play` and `bgm_request`); `game.music` is the CD track `bgm_request` picked.
The trace samples at the same point as the emulator's tracer.

**What is presentation.** Sprite objects are kept in full because logic reads them (animation
ends, debris slots, the professor's sprite position, the idle character's x, image comparisons
in the stage select) and because they are exactly what the renderer needs in Phase 7. Image
uploads to VRAM (`item_load`), GPU, CD and SPU calls are left out; the renderer and the audio
layer replace them.

**Code style.** Each ported function names its original (`play_fall`, `FUN_800A9F18`, …) and
keeps its order of reads and writes, its integer arithmetic and its quirks. Per-player arrays go
through `g.pv(address)` (the current player's word) and objects through `g.ob` (0 or 400).

## 3. Porting method

1. **Decompile** PAZLE.EXE in full with Ghidra and ghidra_psx_ldr (CLAUDE.md's command) plus
   `re/ghidra/EnableParamId.java` (§8), and apply the hand-given names from
   `re/symbols/PAZLE.game.tsv` and `PAZLE.vars.tsv`.
2. **Port screen by screen** in the order the corpus reaches them, reading each function's
   decompilation (and its disassembly where the decompiler is unsure), table addresses from the
   code.
3. **Compare** with `npm run trace` after each screen. The replay stops at the first tick where
   any field differs and prints the ticks before it; screens not yet ported stopped the replay
   with a "not ported" marker, which kept the comparison honest while the port grew.

Gameplay matched from its first run; so did the menus, the map, the story scene and player 2's
idle screen. The traces then confirmed each later screen as it was added.

Phase 5's corpus never reached the zone clear, the ending, name entry or the stage select. Three
new movies reach them, with a new movie directive (`docs/re/oracle-harness.md` §2):
`poke TICK ADDRESS VALUE [SIZE]` writes memory right after tick TICK is recorded, in the
emulator and in the core alike. A poke of the professor's row to 15 makes him reach the goal at
once, so a stage can be cleared without playing it.

with `scripts/run-movie.sh`.

## 6. Function-level checks (Unicorn)

starting memory the core uses (plus the state pointer `pazle_main` stores at `0x800ED328`),
writes a generated game state, calls one original routine and records:

- every 32-bit word that changes in PAZLE.EXE's data and BSS and in the shared state block;
- the return value;
- the `rand()` calls (the BIOS stub is replaced by the LCG) and the arguments of `se_play` and
  `bgm_request` (replaced by recorders); `item_load` is skipped.

## 8. Findings

**New facts about the game** (the spec pages are updated):

- **Clearing a stage adds a time bonus** (`0x80099128`, during the goal sequence): 20,000 points
  if the stage clock shows under 10.0, otherwise `((600 − t) × 40 + 90) / 100 × 100` for
  t < 600 tenths, nothing after 60.0. Every third stage (the one with the bonus marker,
  `(stage + 1) % 3 == 0`, not in 100-stage mode) also adds a **piece bonus** from a table by
  stage group and pieces used (`0x800E2920`), and awards a collectable item shown at game over.
  `lines.md` §5's "nothing else scores" holds for play itself only.
- **The stage clock starts one tick in.** Loading a stage draws the best time with
  `FUN_800B0C04`, which also calls `stage_timer_tick`, so the sub-counter starts at 5.
- **One- and two-line clears reset `lines_this_clear` on the same frame**: the pop-up
  dispatcher's entries 0-2 clear it; only 3 and 4 lines keep it while their pop-up shows.
- **The continue screen and the save screen reuse variables**: the countdown runs on
  `stage_time_sub`; the zone-clear screen runs the continue screen's steps 4-7 (wipe, items)
  through a borrowed step word.
- **100-stage mode pauses itself** as soon as play first starts (`pause_check`'s forced case),
  and the pause screen then opens the stage select: choosing a stage is the first thing the
  player does.
- **Two text-box variants**: the ending's (`FUN_800BFF24`) speeds up with Cross or Circle held,
  spaces two-part characters differently and uses different prompt objects.
- **The goal sequence walks the professor to the middle** (x = 40 px) before the bonus marker
  and the next stage's walk-off.

**Tooling:**

- **Ghidra drops call arguments** that a function passes straight through to another one (for
  example `FUN_80098658(n, image, x, y)` forwarding `a0`-`a3`), so calls read as `f()`. Turning
  on the "Decompiler Parameter ID" analyzer (`re/ghidra/EnableParamId.java`, a pre-script)
  fixes it. Add `-preScript EnableParamId.java` to the whole-EXE decompile command.
- **`re/tools/disasm.py`** disassembles a function by its call-graph extent, for the places
  the decompiler is unsure about.
- **The state pointer** (`0x800ED328`) is only set by `pazle_main`; running routines in
  isolation (Unicorn) needs it set first, or every `state+…` access goes elsewhere.

## 10. How the next phases use the core

- **Phase 7 (renderer):** draw the sprite objects in `game.m` (`state+0x5C`, 1,050 × `0x7C`
  bytes: position, scale, rotation, kind, image, priority, flip, palette) the way `objects_draw`
  sorts them, plus the few immediate-mode boxes (`FUN_800B4344`, fades).
- **Phase 8 (audio):** play `game.se` and `game.music` per tick.
- **Phase 9 (shell):** call `game.step(pad)` at 59.826 Hz with the keyboard/gamepad word; keep
  pad 2's Start masked; replace the memory card with browser storage at screen 13 and the
  menu's Continue; leave Puzzle Mode when `game.exited`.
